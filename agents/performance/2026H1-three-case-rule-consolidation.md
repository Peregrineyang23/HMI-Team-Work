## 2. 可合并进入主线的规则

这些规则在三份材料中反复出现，且不依赖具体个人，应提交到主线规则：

1. **分数与档位必须机械一致。**  
   90+ 才能标 A；75-89 标 B。若有管理校准，必须同时写 `evidence_adjusted_score` 与 `manager_calibrated_score`，不能用低分直接挂高档。

2. **证据状态文件必须自洽。**  
   `evidence-index.csv`、`self-evaluation-summary.md`、`evidence-gaps.md`、xlsx 四件套必须一致。已解决的授权/数据源不能在 gaps 里继续标缺失。

3. **数量型数据只证明密度或复杂度。**  
   Figma 版本数、会议数、消息数、文件数、代码行数、人天数、ticket 引用数都不能单独证明质量、采纳、低返工、沟通质量或个人影响力。

4. **A 档质量必须有采纳/评审/闭环证据。**  
   设计质量 18/20 以上、协作 4/4、风险闭环 5/6 以上、AI 提效满分、加分项，都需要至少一条可复核的质量或影响证据。

5. **本地工作流进入评分，但必须去重和标注采用状态。**  
   Blender、AE、ME、音频、Unity、DCC、Agent/MCP、插件、脚本可以作为证据；但要区分源文件、自动保存、临时文件、下载资产、最终采用版本和团队共享资料。

6. **手填数据与挖掘数据分层。**  
   人天表、周报、个人总结属于人工维护原始数据；从中聚合出的工时、主题簇、ticket 计数是数据挖掘结果。前者支持范围和节奏，后者支持趋势；二者都不能单独证明质量。

7. **加分项要防止重复计算基础职责。**  
   方法论、主导专项、外部好评、业务指标提升，只能在“超出本职 + 有额外影响证据”时加分。没有书面好评或指标时，外部认可类加分应为 0。

8. **AI 提效需要 adoption 或 before/after。**  
   代码体量、MCP 数量、脚本数量只能证明工具链复杂度；要证明提效，需要运行日志、节省时间估算、被他人复用或具体项目落地记录。

9. **共享文件贡献按占比和角色折算。**  
   在大型共享 Figma/本地资源库中，低编辑占比只作为参与或背景证据，不能直接支撑主责或高质量贡献。

10. **管理校准必须写触发条件。**  
   每个上探区间都要写清楚触发条件，例如补 Figma raw、Jira 关闭状态、客户/PM 采纳、源文件索引、团队复用记录。

## 3. 应剔除、不进入主线的内容

以下内容不应提交为主线规则：

| 内容 | 剔除原因 |
| --- | --- |
| 某个人的项目、分数或排名 | 会造成员工 Agent 泄露或互相比对。 |
| “某类证据多就自动高分” | 会奖励数据暴露程度，而不是绩效价值。 |
| “代码行数/文件数/消息数/会议数直接转分” | 三个案例都证明这种做法会膨胀。 |
| 个人化赛道权重 | 李颖 AI、李玮本地资源、余宗历人天主线都只能作为角色校准，不应改变一级权重。 |
| 未经复核的外部好评、用户满意度、业务指标 | 没有书面/原始证据不能作为通用加分规则。 |
| 周期外产出直接计分 | 2026-07 数据只能背景化，除非管理者明确批准。 |

## 4. 主线提交判断

建议 **提交到打分主线规则，但只提交通用规则，不提交个人案例细节**。

提交范围：

- 更新 `01-unified-data-mining-and-scoring-rules.md` 的校准规则；
- 增加分数/档位一致性；
- 增加四件套一致性校验；
- 增加手填数据 vs 数据挖掘数据分层；
- 增加本地工作流去重和采用状态；
- 增加 AI 提效与加分门槛。

暂不提交：

- 李颖、李玮、余宗历的具体得分；
- 三人的项目名、证据 ID、排名；
- 小范围对比结论；
- 任何真实姓名与证据映射。
