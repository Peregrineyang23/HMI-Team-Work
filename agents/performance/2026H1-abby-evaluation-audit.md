## 一、总体判断

Abby 这份评估包的打分方法论是当前几份自评中最接近“可复核绩效材料”的一版。它没有只堆叙事，而是把 Unity、DCC、本地文件、Figma API、飞书文档、飞书消息、Git 记录、过程性工作边界和置信度分级都放进了统一 SOP。这个方向与我们之前确定的 `evidence_score != performance_score`、本地工作流补证、置信度折算、人工复核保留空间等原则一致。

需要校准的是 Excel 里的实际给分。李玮在 Abby 表中的最终分为 93.5，档位 A；而当前 v0.2 团队模型在未接入 Abby 新证据前给出的模型建议分为 83.0，档位 B。差异主要来自 Abby 新增了 Figma、本地资源、飞书文档、消息密度和项目问题闭环证据。这个差异方向合理，但 93.5 偏积极，建议经 raw evidence 复核后落在 89-92 区间；如果 Figma raw、本地文件索引、关键评审结论和问题闭环记录都能复核，A 档可成立。

## 二、Abby SOP 方法论校验

### 与既有模型一致的部分

| Abby SOP 要点 | 与 v0.2 模型关系 | 校验结论 |
| --- | --- | --- |
| 证据优先，不用纯叙事支撑高分 | 对应 evidence / confidence 权重 | 一致 |
| 本人贡献优先，不把团队成果直接算个人贡献 | 对应 person attribution / confidence | 一致 |
| 时间边界明确，周期外只做背景 | 对应 timestamp_in_period | 一致 |

| DCC 工作看源文件、导出物、版本时间线 | 对应本地工作流补证 | 一致 |
| 飞书消息只作沟通密度，不单独证明质量 | 对应证据分级 | 一致 |
| 权重沿用原评价表，不因某类证据多而私自改权重 | 对应维度权重稳定 | 一致 |
| 加分项更谨慎，扣分项必须有明确证据 | 对应 bonus cap / negative evidence | 一致 |

### 方法论亮点

1. 将 Unity 引擎内调试、DCC 版本迭代、多电脑产出、线下评审等“传统不可见工作”放到证据边界里，而不是把它们忽略。
2. 明确区分 S/A/B/C/D 级证据，这比单纯“文件数、消息数、会议数”更适合绩效复核。
3. Figma API 证据规则写得比较克制，承认版本历史不能提供完整节点级 diff。
4. 对 Git 证据的局限判断是对的：Git 是 Unity 工作重要证据，但不能覆盖本地调试、多人代提交、二进制资源 diff 难解释等情况。
5. “本地文件不能单独证明客户满意度、是否上线、是否本人独立完成、是否无返工”这一条非常关键，建议纳入团队通用规则。

## 四、主要风险与校准点

### 1. 93.5 分偏积极

基础分 91.5 已进入 A 档，再加 2 分后达到 93.5。这个结果对“自评优化版”可以理解，但作为绩效评审基础，建议更谨慎：

- 未复核 raw evidence 前：建议区间 88-90。
- 复核 Figma raw、本地文件索引、飞书文档/周报、问题闭环记录后：建议区间 90-92。
- 只有在明确有客户/跨部门认可、关键项目主责、最终采用记录时，93+ 才更稳。

### 2. 本地资源数量不能直接等同个人贡献

表中引用了红旗资源 1425 个 / 79.7GB、车载游戏 3634 个 / 7.4GB、红旗 DLP 大灯 515 个 / 1.48GB。这些能证明项目复杂度和资料规模，但还不能直接证明个人独立贡献比例。需要补：

- 文件 owner / 作者 / 创建者；
- 修改时间是否在 2026H1；
- 源文件与最终交付的对应关系；
- 是否第三方资料、客户资料、团队共享资料；
- 是否为最终采用版本。

### 3. 飞书消息数量只支撑沟通密度

红旗相关至少 250 条、车载游戏 72 条，是很好的协作活跃证据，但当前说明里也承认接口返回消息 ID，未展开正文。因此它不能单独支撑“沟通质量满分”或“减少返工”。建议作为协作维度的中高置信补证，而不是 S 级证据。

### 4. 2026 年 7 月内容需要折算

SOP 已注明 7 月版本只作项目延续背景，不直接计入 H1 核心评分。后续如果 Excel 证据摘要或支撑论据引用 7 月数据，需要明确标注“背景，不计入核心分”或按比例折算。

### 5. AI 工具提效满分需补效率证据

AI 工具提效 2/2 的理由目前更多是“AI 相关项目和资料整理存在”，还缺少提效百分比证明。建议补：

- AI 参与前后耗时对比；
- 自动生成/整理的具体材料；
- 被团队复用的脚本、提示词、流程；
- 人工修改比例。

### 6. 加分项 2 分需要“主导重大专项”证明

当前加分项为“主导重大设计专项，效果显著”+2。这个加分可以考虑保留，但需要把“主导”拆清楚：

- 主导范围是红旗车载游戏、DD010 Car Visualization、车载游戏适配，还是某个设计专项？
- 结果是否有明确交付、采用、评审通过或业务影响？
- 是否存在其他共同 owner，避免把团队成果全部归到个人。

## 六、归纳后的可复用打分思路

建议把 Abby SOP 中的方法吸收进团队通用绩效模型，形成“主线 + 证据 + 置信度 + 校准”的流程：

1. 先确定主线贡献：项目主责、领域 leader、组织职责、跨项目支撑。
2. 再建立证据矩阵：S 级直接证据、A 级强相关证据、B 级辅助证据、C 级本人说明、D 级不采信。
3. 对每个子项只引用能直接支撑该子项的证据，过程性工作放到边界说明或证据规则，不在单项里泛化兜底。
4. 用原评价表权重打基础分，不因为某人某类证据丰富就改变一级权重。
5. 对本地文件、Figma 版本、飞书消息、Git 提交做去重和周期折算。
6. 加分项必须有额外影响力证据，不能只是基础职责的重复加分。
7. 输出时给出“建议区间”，而不是只有单点分数。

## 七、建议结论

对 Abby / 李玮这份材料的管理判断可以这样写：

> Abby 这套自评方法论是可采纳的，尤其适合补足 Unity、DCC、本地文件和过程性设计工作的不可见投入。李玮在红旗8397、车载游戏、DD010 车辆可视化、设计系统和 Unity 还原相关主线中确有高复杂度、多项目、多工具链贡献。当前 93.5 分作为自评优化版略偏积极；在未完成 raw evidence 复核前，建议管理者校准区间为 88-90；若 Figma raw、文件索引、问题闭环和关键评审记录均能复核，A 档边界或 90-92 分可成立。

5. 对飞书消息抽样展开正文，验证 250/72 条消息中多少为任务推动、设计决策、反馈闭环。
6. AI 提效部分补具体工具链、使用次数、节省时间或复用人群。
