# 设计团队绩效量化与 KPI 指引（员工公开版）

- release_level: PUBLIC_DESENSITIZED
- policy_basis: 2026H1 performance rules v0.7
- effective_for: 后续绩效周期与日常 KPI 记录
- published_at: 2026-07-23

## 1. 为什么要做量化

绩效量化不是比谁提交的文件多、消息多、会议多，也不是用机器替代管理判断。它希望解决三件事：

1. 让真正创造价值的工作被看见，包括线上协作、本地设计、项目推进、问题解决、方法沉淀和团队支持。
2. 用同一套证据和评分口径降低信息差，让不同岗位、不同项目和不同在岗周期的人获得公正评价。
3. 引导团队竞争集中在质量、结果、责任、复用和长期价值上，而不是材料包装和数量堆积。

团队希望形成的工作习惯是：**业绩可见、贡献可归因、结果可验证、信息真实完整。**

## 2. 基本原则

### 2.1 结果优先，不以量取胜

文件数、页面数、版本数、节点数、消息数、会议数、任务数和工作时长只能说明工作范围或复杂度，不能直接换算绩效分。

高价值贡献通常需要回答：

- 解决了什么重要问题；
- 本人的角色和独立贡献是什么；
- 结果是否被采用、验收或复用；
- 对质量、周期、风险、效率或团队能力产生了什么影响。

### 2.2 证据服务于公平，不制造材料竞赛

证据的作用是减少遗漏和错误归因，不是鼓励额外制造汇报材料。已有的设计源文件、版本记录、评审意见、任务状态、交付记录和验收反馈应优先复用。

证据暂时缺失不等于工作没有发生。员工可以补充背景和线索，由主管进一步交叉验证；未经验证的自述不会被当作高置信度成果，也不会仅因系统没有记录就自动判定为零贡献。

### 2.3 真实高于好看

自评应同时写成果、限制、未完成事项和需要主管确认的部分。夸大归属、重复计数、把团队成果全部计为个人成果、把周期外工作计入本周期，都会降低证据可信度。

### 2.4 同权重、按角色校准

所有成员使用相同的五项权重。项目负责人、设计执行者、协作组织者、平台建设者和 AI 工作流建设者可以使用不同类型的有效证据，但不会因为岗位更容易产生文件或消息而天然获得更高分。

## 3. KPI 评分结构

基础评分由五个维度组成：

| 维度 | 权重 | 重点评价内容 | 高价值证据示例 |
| --- | ---: | --- | --- |
| UI/UE 设计产出与质量 | 50% | 交付质量、完整性、一致性、可实现性、源文件与文档规范 | 最终采用、评审通过、低返工、实现一致、明确验收 |
| 项目进度与执行力 | 20% | 节奏、节点、需求落地、风险管理、问题闭环 | 里程碑按期完成、风险提前暴露并关闭、关键问题解决 |
| 设计能力与沉淀、AI 工具利用 | 15% | 专业成长、方法沉淀、创新、工具提效和复用 | 方法被复用、流程前后效率对比、跨项目采用、可重复运行记录 |
| 团队协作与沟通 | 10% | 信息同步、跨角色协同、决策推进、团队贡献 | 明确决策、责任分配、依赖关闭、减少返工、帮助团队完成结果 |
| 工作规范与责任心 | 5% | 主动性、可靠性、规范、承诺与问题担当 | 按承诺交付、资料可追溯、问题主动跟进、风险不隐瞒 |

最终结果按以下关系核对：

`最终分 = 五项基础分合计 + 经确认的加分 - 有明确依据的减分`

- 加分只用于超出岗位基础职责的增量价值，不能与基础分重复计算。
- 减分必须有明确事实和评价依据，不根据印象或单一模糊信号直接扣分。
- 每项加减分都应写明个人角色、增量价值、结果依据和不重复计分说明。

## 4. 分档参考

| 档位 | 分数 | 主要条件 |
| --- | ---: | --- |
| A | 90-100 | 关键结果或平台级贡献突出；质量、交付和影响有多源证据；没有重大未闭环风险。 |
| B+ | 85-89 | 多项贡献稳定且证据较完整；表现明显高于基本要求，但长期复用或最终影响仍可加强。 |
| B | 75-84 | 能稳定完成岗位核心职责，交付和协作达到要求。 |
| C | 60-74 | 有实际交付，但质量、可靠性、闭环或证据完整性存在明显不足。 |
| D | 60 以下 | 核心职责缺少有效交付，或存在明确的重大问题。 |

档位按岗位责任和实际结果校准，不按原始工作数量排名，也不以员工之间的文件数、消息数或在线时长进行简单横向比较。

## 5. 什么样的贡献更容易被准确识别

一项完整、可复核的业绩记录应尽量包含：

| 字段 | 需要说明的内容 |
| --- | --- |
| 时间 | 工作发生和交付的周期 |
| 目标 | 要解决的问题或承担的任务 |
| 角色 | 主责、共同负责、协作、评审或支持 |
| 行动 | 本人完成的关键设计、决策、推进或问题解决 |
| 结果 | 采用、验收、上线、风险关闭、效率改善或复用情况 |
| 证据 | 设计版本、任务记录、评审结论、交付物、文档或脱敏反馈 |
| 限制 | 尚未验证的内容、团队共同贡献和待补证部分 |

推荐使用一句话结果表达：

> 在 `<时间>`，我作为 `<角色>`，为 `<项目代号/任务>` 完成 `<关键行动>`，结果是 `<采用/验收/影响>`，可通过 `<脱敏证据>` 复核。

## 6. 证据可信度

| 等级 | 定义 | 使用方式 |
| --- | --- | --- |
| S | 有时间、有归属、可访问并能对应结果的直接证据 | 可支持精确评分和高档结论 |
| A | 与贡献强相关，但仍需补充归属或结果验证 | 可支持较强结论，建议交叉验证 |
| B | 只能说明工作范围、参与度或复杂度 | 作为辅助背景，不能单独证明质量 |
| C | 个人说明或暂时无法复核的信息 | 进入补证和人工确认 |
| D | 无法归属、超出周期、不可验证或与评价无关 | 不进入评分 |

高置信度通常来自至少两类信息的相互印证，例如“交付物 + 验收记录”“设计版本 + 评审结论”“任务关闭 + 最终采用”。

## 7. 认可、点赞和一稿过如何计入

- 与具体交付物绑定的客户或业务方书面验收、主管明确确认价值、可验证的一稿通过，属于高置信度认可。
- 设计工具或协作文档中的明确评审结论，可以支持质量、响应和采用判断。
- 点赞、表情和简短回复是积极信号，但单独不能证明设计质量或业务价值。
- “收到”“辛苦了”等通用回复只说明信息触达或协作过程，不自动产生质量加分。
- 同一份认可如果已经用于基础质量评分，不能再次作为完全相同价值的加分。

## 8. 本地工作、AI 和协作工作如何计入

### 本地设计工作

Blender、After Effects、Photoshop、3ds Max、Sketch、Unity 等本地工作均可纳入。源文件、导出文件、修改时间和哈希可证明工作存在，但临时文件、自动保存、素材下载和连续渲染帧需要去重；最终仍要结合个人角色和采用结果。

### AI 工具与自动化

使用 AI 工具本身不直接加分。有效贡献需要体现至少一项：

- 工作流被实际采用；
- 有使用前后的时间或质量对比；
- 可以稳定重复运行；
- 被其他成员或其他项目复用；
- 解决了过去难以解决的问题。

脚本数量、提示词数量、模型数量和生成图片数量只能说明活动规模，不能单独证明效率和价值。

### 协作与组织工作

会议和消息不是最终成果。高价值协作应体现决策形成、责任明确、依赖关闭、风险解决、返工减少或跨团队结果达成。支持型角色不会因为设计文件较少被低估，但需要把组织行为与项目结果连接起来。

## 9. 短周期员工的公平规则

- 不使用“在岗月数除以完整周期”直接乘总分。
- 产出数量、项目数和任务数按实际在岗月份归一化后再参考。
- 质量、验收、协作、责任心和岗位完成度在实际观察期内完整评价。
- 观察周期不足三个月时，高档结论需要更明确的个人归属和验收证据。
- 学习活动、继承文件和正常入职适应不会被包装为额外加分，但在短周期内形成的真实高价值结果可以正常评价。

## 10. 后续 KPI 运行节奏

### 日常与每周

- 在原有项目工具中保留任务、版本、评审和交付记录，不额外制造无价值材料。
- 对关键结果补充个人角色、结果和证据入口。
- 对线下、本地或口头完成的关键工作，用简短工作记录补齐时间和验证人。

### 每月

- 更新一次个人成果索引，优先记录已采用、已验收、已闭环或已复用的结果。
- 标记工作属于主责、共创还是支持，避免归属模糊。
- 主动列出证据缺口和未闭环风险，不等到绩效周期结束集中补材料。

### 每季度或重要里程碑

- 由项目负责人和成员共同确认关键成果、个人角色和采用状态。
- 对高价值方法、AI 工作流和平台资产检查是否发生真实复用。
- 对目标变化、资源变化和跨团队依赖留下校准记录。

### 半年度与年度

- 员工基于成果索引提交自评、证据区间和待确认问题。
- 主管结合岗位预期、项目结果、证据可信度和组织贡献进行最终校准。
- 最终分、档位、加减分和评价依据应保持一致并可复核。

## 11. 员工的确认与补证权利

员工可以：

- 核对项目和成果是否遗漏；
- 纠正个人角色、时间范围和贡献归属；
- 对低置信度结论补充证据或说明；
- 指出重复计分、错误归因和周期外数据；
- 要求了解影响本人评分的主要事实依据。

横向排名、其他成员成绩和私人证据不属于个人 Agent 的分析范围。员工 Agent 只能分析被明确授权的本人数据。

## 12. 数据与隐私边界

员工和 Agent 不得在材料中提交访问令牌、API 密钥、登录二维码、私人联系方式、个人身份信息、未获授权的聊天原文、客户敏感原文或本地绝对路径。

对外共享时使用项目代号、成员别名、脱敏路径、时间、文件类型、哈希前缀和结果摘要。原始敏感证据只在有权限的管理校准范围内复核。

## 13. 我们鼓励的竞争

团队鼓励：

- 把重要问题真正解决；
- 做出可采用、可实现、可持续的设计；
- 提前发现并关闭风险；
- 建立能被他人复用的方法和工具；
- 帮助团队减少返工并提高整体交付质量；
- 如实呈现贡献、限制和共同成果。

团队不鼓励：

- 用文件、版本、消息、会议或在线时长堆高存在感；
- 为了个人可见度拆分任务或重复提交同一成果；
- 隐藏风险、抢占团队成果或只选择容易展示的工作；
- 把工具使用、加班时长或材料包装直接等同于绩效。

最终目标不是让每个人更擅长“证明自己很忙”，而是让真正重要、真实且可持续的贡献得到公正认可。
